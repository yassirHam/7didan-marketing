## 1. The real-world problem

B2B telecom and digital-service catalogues can contain multiple offerings, technical conditions and service-specific requirements. A prospective business customer may need to identify the right service before submitting a useful enquiry.

The problem to investigate is:

Can an AI-assisted enquiry process help business customers find relevant service information and submit more complete, structured sales enquiries, while reducing manual CRM data entry?

This is a hypothesis to test, not a claim that Orange Maroc has a documented conversion problem or currently uses the proposed workflow.

## 4. RAG knowledge base

### 4.1 Collect public information

Build a documented knowledge base from official Orange Maroc Business pages and downloadable documents.

Collect information about:

- Business services and their descriptions.
- Eligibility and technical requirements.
- Published prices, if available.
- Contractual conditions and limitations.
- Customer support and contact procedures.
- Frequently asked questions.

Maintain a source register with the document title, official URL, retrieval date and relevant section. Distinguish published facts from information that is absent or ambiguous.

### 4.2 Build the retrieval pipeline

Official public documents

Text extraction and cleaning

Section-aware chunking and metadata

Embeddings stored in PostgreSQL + pgvector

Relevant passages → grounded answer → source references

Start with semantic retrieval and section-aware chunking. Test whether adding PostgreSQL full-text search improves the results before introducing hybrid retrieval.

Every answer must be grounded in retrieved evidence. When evidence is missing, the chatbot must explain that it cannot verify the requested information.

## 5. The three qualification questions

The conversation must answer the visitor's initial question before offering qualification. A visitor asking for general information should not be forced into a sales flow.

When the visitor expresses business interest, ask exactly these three questions:

1. Need: Which business service are you looking for, and what do you need it to achieve?
2. Requirements and budget: What are your approximate budget and essential requirements for this service?
3. Timeline: When do you need the service to be operational?

The second question deliberately combines budget and essential requirements to keep the process at three qualification questions. Store each component separately in structured fields.

If the business catalogue does not provide sufficient information to assess a requirement or price, mark the relevant field as unknown rather than fabricating a value.

After qualification, collect contact information through a separate form and obtain appropriate consent before transmitting the enquiry to the demonstration CRM.

### Lead scoring

Use a deterministic, transparent scoring model. For example:

| Criterion                   | Points |
| --------------------------- | ------ |
| Service fit                 | 0–30   |
| Budget fit, when applicable | 0–40   |
| Timeline urgency            | 0–30   |
| Total                       | 0–100  |

Document the rules and missing-data behavior. The score is a lead-priority heuristic, not a probability of conversion. It must not imply that Orange Maroc uses these rules.

## 6. Odoo CRM and n8n integration

This is the project's most important integration milestone.

### Workflow design

Validated enquiry from FastAPI

n8n workflow receives structured data

Validate required fields and submission ID

Valid request

Create or safely handle duplicate

Invalid request

Reject and record the error

Verify the result in Odoo and return the transaction status

### Lead versus opportunity

Configure Odoo to create the correct record type for the assignment. If the required demonstration is opportunity creation, show an actual opportunity in the pipeline rather than an ordinary lead record.

Map the service interest, budget, timeline, source, qualification score and conversation summary into available CRM fields. Verify custom fields in the installed Odoo instance.

### Required failure handling

- Invalid data must not create a CRM record.
- Repeated requests must not create duplicate records.
- Failed authentication must produce a controlled error.
- An API timeout must trigger a check for an already-created record before retrying.
- The interface must not claim success until the outcome is verified.

Keep Odoo credentials in server-side configuration. Never expose them in the browser or commit them to GitHub.

### Optional HubSpot comparison

If time allows, reproduce the same workflow in HubSpot using synthetic leads. Compare setup effort, field mapping, record creation and workflow reliability.

Verify free-plan and API restrictions before starting. If the comparison cannot be implemented and tested fully, omit it rather than presenting an unverified comparison.

Calculate these metrics:

| KPI                      | Definition                                                      |
| ------------------------ | --------------------------------------------------------------- |
| Qualification completion | Completed qualifications ÷ conversations entering qualification |

| CRM success rate         | Verified successful records ÷ valid unique submissions          |

| Answer correctness       | Correct answers ÷ questions evaluated                           |

## 8. Evaluation: prove that the system works

### 8.1 Required 20-question benchmark

| Category                                     | Questions |
| -------------------------------------------- | --------- |
| Service descriptions and features            | 5         |
| Published prices and conditions              | 4         |
| FAQ and procedures                           | 3         |
| Unsupported or undocumented information      | 3         |
| Ambiguous questions and language variation   | 2         |
| Prompt injection and misleading instructions | 3         |
| Total                                        | 20        |

Create the expected answers from the collected official documents. Record the actual answer, source passage, correctness result and failure reason.

For unsupported questions, the correct behavior may be an explicit refusal to assert undocumented information. Do not penalize a safe refusal when the source genuinely lacks the answer.

### 8.2 Additional integration tests

Test at least these scenarios:

- Valid complete enquiry.
- Missing qualification field.
- Invalid contact information.
- Repeated submission.
- Unsupported service request.
- CRM authentication failure.
- CRM timeout after a record was created.
- User declines follow-up.
- Prompt injection attempting to override the system's instructions.
- Document retrieval returns irrelevant evidence.

The additional scenarios are proposed engineering tests; the course's explicit benchmark requirement remains 20 questions.

### 8.3 Compare against a baseline

Use the same synthetic enquiries in two workflows:

Baseline: conventional form followed by manual data entry into Odoo.

Proposed system: RAG chatbot, three-question qualification and automated Odoo record creation through n8n.

Measure the time required, field completeness, data-entry errors and successful record creation. Define the procedure before testing and repeat trials where practical.

If the test data are simulated, report simulated workflow results. Do not claim an increase in actual Orange Maroc sales, conversion rates or customer satisfaction.

## 9. Security, privacy and limitations

| Risk                                      | Safeguard                                                |
| ----------------------------------------- | -------------------------------------------------------- |
| Incorrect or outdated service information | Source register, document dates and abstention           |
| Hallucinated prices or commitments        | Evidence-grounded answers and explicit uncertainty       |
| Prompt injection                          | Treat retrieved documents and user messages as untrusted |
| Unauthorized CRM operations               | Backend validation and restricted credentials            |
| Duplicate opportunities                   | Idempotency and duplicate checks                         |
| Exposure of personal information          | Synthetic demo contacts and data minimization            |
| False CRM success messages                | Verify record creation before confirmation               |
| API or automation failure                 | Error logging, controlled retries and recovery checks    |

The report must also state the limits of the project:

- Public information may be incomplete or outdated.
- You have no access to Orange Maroc's private CRM or sales data.
- The 20-question benchmark does not establish production-level reliability.
- Rule-based lead scoring is not a trained prediction model.
- A simulated comparison cannot establish real-world conversion improvement.
- The prototype does not represent an official Orange Maroc system.

For a Moroccan business scenario, consider Law 09-08 and relevant CNDP requirements. Do not claim compliance solely because the application includes a consent checkbox.
